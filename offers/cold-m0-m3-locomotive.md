# Холодка M0–M3 + PM × локомотив → партнёрство A

**Статус:** оценка модели + схема внедрения  
**Связь:** `docs/agency-offer-architecture.md` · `offers/locomotive-pilot-envelope.md` · `offers/locomotive-logic-cold.md`

---

## 1. Оценка вашей модели (честно)

### Что сильно

| Элемент | Почему это правильно |
|---|---|
| M0 рейтинг до касания | Как ABM: не спамим всех, фильтруем ICP |
| M1 триггеры + win + крючок на созвон | Первый контакт = ценность, не «прайс» |
| RAG по нишам + по Impro из Bitrix | Агенты не выдумывают услуги — опираются на реальность агентства |
| M2 ветвление исходов | КП / nurture / партнёрам / light / отказ — зрелая воронка |
| Оценка менеджера в M2 | Контроль качества продажи, не только «сделки» |
| PM с недельными триггерами и петлёй в M1 | Система учится; клиент не «продан и забыт» |
| Связка с Bitrix end-to-end | Единый мозг данных |

Это ближе к **agentic ABM + sales ops**, чем к классической холодке агентства. По масштабу — выше рынка mid-agency.

### Где риски / поправки

| Риск | Суть | Как закрыть |
|---|---|---|
| M2 тянет в B по умолчанию | Агенты «любят» продавать SEO/кусочки — проще и в каталоге | Жёсткий **трек A/B** с M0; локомотив = default для A |
| M3 «сразу договор на партнёрство» | Рынок почти никогда не подписывает годовой AOR с первого касания | M3 = договор на **пилот / вход**, стратегия пути к A |
| Крючок «идеи к вакансии» | Звучит как подрядчик | Крючок = **пилот функции / мост найма** |
| Дублёр на созвоне в realtime | Технически тяжело + риск «робота в ухо» | Сначала async prep + post-call; realtime — фаза 2 |
| Перегруз M1 аналитикой | Долго до первого касания → остывает база | SLA: M1 light за X часов, deep — только top-score |
| Передача партнёрам | Ок, но не должна съедать A-fit аккаунты | Правило: A-fit не отдаём на чистый SMM без эскалации |

### Вердикт

Модель **рабочая и выше рынка** как операционная система холодки.  
Чтобы она вела к стратегическому партнёрству, нужно одно решение:

> На каждом этапе явно жить в логике **трек A / трек B**, а локомотив вшить как **единственный правильный первый продукт для A**.

## 2. Как делают другие (сжато)

Типовой путь агентств, которые дорастают до AOR / большого бюджета:

```
ICP score → персональный хук → discovery call
  → paid pilot / foot-in-the-door (исполнение, не план)
  → decision meeting
  → retainer / envelope / % 
  → account growth (PM)
```

Ключевые правила рынка:

1. С холодки не продают «партнёрство на год» — продают **вход, который логично расширяется**.  
2. Пилот платный (фильтр серьёзности); часто **зачёт** в следующий контракт.  
3. Success criteria пилота пишут **до** старта.  
4. Expansion — отдельный ритуал (decision meeting), не «а давайте ещё SEO».  
5. CRM хранит: fit, трек, триггеры, next offer, запреты.

Ваша M0–M3+PM это же, только с агентами и RAG. Не хватает явной прошивки **локомотива и трека A**.

---

## 3. Два трека внутри одной холодки

| | Трек A | Трек B |
|---|---|---|
| Цель | Партнёрство / % / годовой бюджет | Кусочек / пакет |
| Локомотив / первый продукт | **Пилотный конверт функции** (LOC-003) | FIX-пакет (SEO, Директ…) |
| ЛПР | Собственник / CEO / коммерческий | Маркетолог / подрядчик-менеджер |
| Сигналы | Вакансия CMO, рост, дыра в функции, новый продукт | «Нужен SEO», узкий бриф |
| M3 договор | Пилот → путь к A | Фикс-scope |
| PM | Расширение контуров маркетинг+продажи+IT | Допродажи кусков / мост в A |

**Правило:** компания может сменить трек, но в карточке Bitrix всегда есть `track = A|B|hybrid` и `north_star = partnership`.

Даже на треке B в PM раз в N недель агент проверяет: «созрели ли под A?»

## 4. Локомотив в системе по стадиям

### M0 — поиск и рейтинг

**Добавить в дашборд рейтинга поля A/B:**

| Поле | Зачем |
|---|---|
| `fit_A` (0–100) | Потенциал партнёрства |
| `fit_B` (0–100) | Потенциал кусочка |
| `track_recommend` | A / B / skip |
| Сигналы A | вакансии CMO/head, рост выручки, новый бренд/линейка, слабый digital, смена агентства |
| Сигналы B | узкий запрос, микробюджет, только канал |

Фильтры ниша/рынок/выручка — ок.  
Для A поднять порог выручки и «оценку масштаба»; микробизнес с высоким интересом → B или skip.

**Выход M0:** список + рейтинг + **рекомендованный трек**.

---

### M1 — аналитика и ЛПР

Цель M1 не «узнать компанию», а собрать **первый крючок на созвон под трек**.

| Если track A | Если track B |
|---|---|
| Company win / personal win ЛПР | Боль канала |
| Триггер (вакансия, рост, дыра) | Конкретный gap (SEO/сайт) |
| Крючок: сравнение с наймом CMO / «функция на 60–90 дней» | Крючок: быстрый фикс + цифра/срок |
| Гипотеза пилотной цели | Гипотеза пакета FIX-* |

**Обязательный артефакт M1:** `hook_call` — одно предложение, почему выйти на созвон **сегодня**.

RAG:

- ниша/рынок из Bitrix  
- **карточка Impro + архитектура A/B + каталог реальных услуг** (чтобы не обещать лишнего)  
- кейсы (когда появятся) только релевантные треку  

**SLA:** top-20% базы — deep M1; остальные — light (иначе воронка захлебнётся).

---

### M2 — диалог, предложение, ветвление

Здесь локомотив **рождается как КП**.

```
Диалог + M1
  → классификация трека (подтвердить/сменить)
  → если A: КП = Пилотный конверт (цель, срок, конверт, decision gate → партнёрство)
  → если B: КП = FIX-пакет / light
  → иначе: nurture / партнёрам / отказ
```

#### Состав агентов M2 (логика, не техспека)

| Агент | Роль |
|---|---|
| Dialogue interpreter | Тейки, возражения, сила интереса |
| Offer architect | Собирает КП строго из реальных услуг A/B |
| Locomotive agent (A) | Только LOC-003 + путь к %/конверту/партнёрству |
| Piece agent (B) | FIX / атомы / цена |
| Coach / QA менеджера | Оценка созвона → воронка управления |
| Call-copilot | Сначала post-call / prep; realtime — позже |
| Outcome router | КП / nurture / партнёры / light / отказ |

**Финалы M2 (ваши) + привязка к цели A:**

| Исход M2 | Смысл | Связь с A |
|---|---|---|
| КП | Офер на стол | A-КП = пилот; в КП явный next = партнёрство |
| Метрики + nurture | Подогрев | Триггеры в карточке ждут M0/M1 signals |
| Партнёрам | Не наш scope | Не сливать A-fit |
| Light ведение | Мини-retainer / часы | Мост; в стратегии путь к A |
| Отказ | Стоп | Причина в базу для обучения |

**Важно:** отдельный контролируемый агент на КП — да.  
Для A у него system prompt: *запрещено предлагать только SEO как главный офер, если fit_A высокий*.

---

### M3 — договор + стратегия пути (не «сразу партнёрство навсегда»)

Переименовать смысл M3:

> Не «заключили стратегическое партнёрство», а **зафиксировали вход и дорожную карту к партнёрству**.

| Документ M3 | Содержание |
|---|---|
| Договор входа | Пилот (A) или FIX (B) |
| Strategy card | Формат сейчас → куда хотим (A) → сроки → инструменты сервиса |
| Handoff в PM/производство | Scope, KPI пилота, accesses, RACI |
| Feedback в M1 | Обучение рейтингов и крючков |

Для A в Strategy card обязательно:

```
Сейчас: пилот / light
Цель: % | партнёрская модель | годовой бюджет
Контуры к захвату: маркетинг → продажи → IT (поэтапно)
Review date: день X decision meeting
```

Договор партнёрства/годового конверта — **часто второй контракт** после пилота (в PM), не обязательный финал первого M3.

---

### PM — машина расширения к A

PM = место, где холодка превращается в партнёрство.

Еженедельно:

1. Триггеры клиента (найм, бюджет, сезон, боль)  
2. План-факт пилота / работ  
3. Удовлетворённость  
4. Гипотезы expansion (какой контур следующий)  
5. Тейки на next touch  
6. Запись в кейсы  

**Ритуал decision meeting** (конец пилота / раз в квартал):

- Показать результат  
- Предложить north_star контракт (конверт / % / партнёрство)  
- Или оставить light / B с честной паузой  

Отсюда можно перезапускать ограниченные M1/M2 на том же аккаунте (upsell), с полной памятью Bitrix.

## 5. Сквозная схема (одна картинка)

```
M0  score + track A|B
 ↓
M1  hook_call под трек (A → функция/пилот; B → кусок)
 ↓
M2  диалог → КП
      A: Пилотный конверт + путь к партнёрству
      B: FIX / light
 ↓
M3  договор входа + strategy card (сейчас → A)
 ↓
PM  исполнение → decision → % / партнёрство / годовой бюджет
      ↑________________ обучение M0/M1 ________________↓
```

**Локомотив** = продукт стадии M2→M3 для трека A.  
**Финальная цель** достигается в PM, не в первом КП.

## 6. Что должно лежать в Bitrix (минимум полей)

| Поле | Стадии |
|---|---|
| track (A/B/hybrid) | M0+ |
| fit_A / fit_B | M0–M2 |
| triggers[] / hooks[] | M1–PM |
| north_star (%, partnership, annual_envelope) | M2+ |
| entry_offer (LOC-003 / FIX-*) | M2–M3 |
| strategy_card | M3–PM |
| call_notes + dialogue_analytics | M2–PM |
| manager_qa_score | M2 |
| next_review_at | M3–PM |
| partner_referral? | M2 |

RAG-корпус для агентов:

1. `agency-offer-architecture.md`  
2. Локомотив + commercial models  
3. Каталог FIX / атомы (для B и для состава внутри пилота)  
4. Кейсы / запреты / ценовые коридоры

## 7. Приоритет внедрения (чтобы не расползтись)

| Фаза | Сделать |
|---|---|
| **1** | Поля track/fit в M0–M1; hook_call шаблоны A vs B |
| **2** | Locomotive agent для КП A; Piece agent для B; outcome router |
| **3** | M3 = договор входа + strategy card → PM handoff |
| **4** | PM weekly triggers + decision meeting template |
| **5** | Call-copilot realtime (после стабилизации 1–4) |
| **6** | Петля обучения M0/M1 на исходах M3/PM |

## 8. Открытые решения

2. Мин. выручка / конверт пилота для трека A в M0?  
3. Light ведение = Partner Retainer (часы) — подтверждаем как мост?  
4. Партнёрам (SMM/нейропрод) — только если `fit_A < X`?  
5. Call-copilot: начинаем с post-call summary + next takes, не realtime?
